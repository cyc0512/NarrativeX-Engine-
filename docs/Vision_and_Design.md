# NarrativeX Engine：架构设计与实现思路

## 一、 项目定位与行业痛点

**NarrativeX** 是一款专门为新一代交互体验 **FluidStory（流态故事）** 打造的底层引擎。

在当前的文字游戏市场中，存在明显的两极分化：
*   **传统视觉小说 (Visual Novel)**：拥有精美的立绘、深厚的剧情羁绊与明确的结局（宿命感），但玩家只能被动点击选项。
*   **纯 AI 聊天游戏**：虽然实现了自由输入与极高的交互性，但往往缺乏主线目标与文学下限，导致玩家在新鲜感过后迅速失去沉浸感。

**NarrativeX 的解决方案**：我们在技术上实现了让“传统视觉小说的叙事骨架”与“大模型的自由灵魂”相融合。开发者使用本引擎，可以创造出一种名为 **FluidStory** 的新型文字游戏——玩家可以像和真人聊天一样用自然语言肆意试探 NPC，但隐藏在底层的状态机与主线收束机制，会将每一次对话的涟漪，最终引向一个不可逆转的既定结局。

## 二、 引擎核心技术架构 (Engine Architecture)

### 1. 完全数据与逻辑解耦 (Data & Logic Decoupling)
*   **剧本驱动**：剧情节点、选项、好感度变化全部剥离至 `story.json`，支持无限扩展。
*   **配置驱动**：引擎的核心人设与 System Prompt 被抽离至独立的配置文件中。开发者在更换游戏主角或修改 NPC 性格时，**无需修改任何 C++ 代码或重新编译**。

### 2. 网络通信与多线程 UI 防阻塞 (Concurrency)
*   采用 `libcurl` 发送标准的 HTTP POST 请求与大模型通信。
*   由于 LLM 响应延迟通常在 1-3 秒，为防止 Qt 主线程卡死，引擎引入了 `QtConcurrent` 多线程框架。UI 在发起请求时进入“思考中”状态，后台线程接收 JSON 返回值后，通过信号槽机制安全更新 UI。

### 3. 动态状态注入 (Dynamic State Injection)
*   **痛点**：静态的 AI 人设会导致 NPC 在整个游戏流程中像个精神分裂的复读机，缺乏剧情连贯性。
*   **方案**：在 `story.json` 的各个节点中加入 `npc_state`（如：“强装镇定”、“极度焦虑”）。C++ 引擎在拼接网络请求前，提取该状态并动态替换 Prompt 中的占位符，使 AI 的反馈严格贴合当前剧情发展。

### 4. 主线收束与危险域拦截 (Mainline Convergence)
*   **痛点**：AI 自由生成缺乏逻辑下限，玩家极端输入容易导致剧情崩塌。
*   **方案**：AI 在返回结果时，需附带意图标签（如 `trigger_event: "danger"`）。当引擎识别到危险信号，将跳过常规节点跳转，强制收束至预先设定的黑化或坏结局节点。

## 三、 数据持久化与平滑迁移 (Persistence)

*   引擎采用 SQLite 存储玩家数据（好感度、当前节点、存档时间），支持多槽位存档。
*   为了防止引擎版本更新导致旧存档失效，`DatabaseManager` 模块实现了数据库结构自动迁移机制：程序启动时通过 `PRAGMA table_info` 检查缺失字段，自动执行 `ALTER TABLE` 补充列，实现旧存档的无缝兼容。

## 四、 品类定义与知识产权 (Concept & IP)

本项目基于行业现状提出并实践了 **DSCR (Dynamic State & Convergent Routing，动态状态与主线收束)** 架构：
*   通过自由文本输入实现玩家意图的无限表达；
*   通过底层状态注入，使 NPC 具备阶段性心理变化；
*   在触碰核心危险域时，采用“主线收束”机制，强制回归至预设剧情结局。

**NarrativeX Engine** 与附带的 **FluidStory** 游戏实例，用于向开发者展示这种结合了自然语言输入与传统宿命感的新型文字交互模式。代码与实例基于开源协议发布。

## 五、 后续演进路线 (Roadmap)
1. **第一阶段（当前）**：完成 Prompt 外部配置抽离，跑通动态状态注入。
2. **第二阶段**：完善“语义级主线收束”，测试 AI 识别危险意图后强制跳转 BAD ENDING 的稳定性。
3. **第三阶段**：优化 Qt 界面的视觉表现（立绘、UI特效），完善工程化打包，提供一键安装包。
